# Local Windows hands-free backend

`kira_voice` uses the installed .NET Framework `System.Speech` dictation recognizer and an enabled female voice matching the configured culture. It prefers Microsoft Zira Desktop when available. It does not download a model, require a cloud key, use a GPU, or import Kira's Core, persona, reference voice or memory. `tts_backend="sapi_com"` explicitly selects the installed SAPI COM female-voice route instead; there is no silent engine fallback. Missing recognition or a matching female voice produces an unavailable error.

This reuses Kira's generic OS speech engine choice, with a new asynchronous host. Studio's Qwen3-TTS voice-design service is a different model and project-storage route, outside this backend. No availability or speech-quality claim is made for that service.

```python
from kira_voice import VoiceController

voice = VoiceController(lambda event: ui_queue.put(dict(event)), culture="en-US")
session = voice.start()       # explicit microphone opt-in
voice.pause()                 # before typed/chat submission
voice.speak(answer, session=session)
voice.resume()                # after a request failure, if still enabled
voice.stop()                  # disable immediately; cooperative device cancellation
closed = voice.close(2.0)     # True only after the host exited; never force-kill
```

Construction, `status()` and `capabilities()` never start a subprocess or acquire a microphone. `start()` returns a monotonic session integer. Stop invalidates the previous session immediately; a stale response can use `speak(..., session=old_session)` safely and is refused. Close is permanent. A retained process awaiting native cancellation cannot be replaced by a second host. `close()` returning False means normal exit is still pending; it is not an exit acknowledgement.

Callbacks receive immutable scalar mappings on background threads, outside controller locks. Queue their contents for Tk or browser delivery. Events have `type`, `session` and `generation`; types are `state`, `transcript`, `capabilities`, `error`. States are `off`, `listening`, `thinking`, `speaking`. Recognition emits one final transcript, then suppresses the microphone while the app thinks and speaks. Speech completion resumes recognition only while hands-free remains enabled. Transcripts marked incomplete are rejected with `transcript_too_long` and never auto-submitted. Errors carry `code` and `fatal`; fatal errors disable hands-free. Capability flags are initially None until the host reports installed support. The app owns its HTTP Origin/client-session protection and request cancellation.

Status contains capability fields (`platform`, `engine`, `stt_available`, `tts_available`, `culture`, `voice_name`, `reason`) plus `state`, `session`, `handsfree_enabled`, `closing`, `pending_stop`, `process_running`. State events may include the original recognition/speech completion session; requested stop alone is not native completion.

Speech and transcripts are bounded to 4,000 UTF-16 units (a supplementary Unicode character uses two units); incomplete recognition is not shortened into an accepted request. JSON command/event lines are bounded to 32,768 characters, the command queue to 16, and event queues to 32. Text is JSON stdin data, never shell interpolation. No audio files or persistent transcripts are created. Slow callback consumers fail closed. A shared Windows `Local\KiraHandsFreeSpeech.v1` named mutex prevents these apps from using speech devices together in the same Windows session; other users/sessions and unrelated programs are outside that lease.

The host is a standard compiled .NET Framework console application. `windows_speech.cs` retains the previously reviewed engine body and adds a normal `Main` entry point. The previous PowerShell source is preserved in the earlier app repositories as history; it is not part of this IdeaForge package and is never launched by this controller. The prior normal script capability attempt was denied by execution policy before the engine ran; no policy setting was changed and no script evaluator or bypass is used.

Build explicitly once with `python -m kira_voice.build_windows_host --build`, using the already-installed Framework64 `csc.exe` and named Framework/System.Speech references. Calling `build_spec()` or running that module without `--build` only returns the fixed build specification. It does not compile, execute speech or create a cache directory. An explicit build writes outside Git under the current user's LocalAppData/KiraVoiceHost, separated by the C# source hash. These apps use that same hash-specific application. Existing outputs and concurrent build locks are refused. A compiler or EXE denial stops the attempt; no other builder, engine, elevation or script route is tried. The helper returns compilation exit/diagnostics and output hash, checks source conservation, and does not run the resulting EXE. Compiler diagnostics are bounded in the returned projection, not by a native process quota; a compilation timeout is a failed build, not a normal-exit claim.

Version 4 rechecks output absence after acquiring the exclusive build lock, so an invocation delayed behind a completed build refuses its output instead of overwriting it. Cleanup attempts one lock-stream close before unlink. If cleanup also fails, `BuildFailure` retains the original primary exception, staged cleanup exceptions, original compiler return and result projection; it never substitutes a cleanup error for the build outcome. A cleanup failure is unsuccessful even if compilation had returned zero. The command-line error projection reports both stages, without rendering arbitrary exception objects.

After that separate build, `capability_probe_spec()` returns fixed `kira-speech-host.exe --mode Capabilities` argv, configuration JSON stdin, an 8-second external timeout and a 4,096-byte output bound. It only returns a specification; it does not compile or execute the EXE. Capability mode enumerates installed recognizers/voices and does not attach a microphone, play speech or acquire the speech-device lease. A separate caller must enforce its timeout/output bound and retain the actual result. Starting hands-free requires the built application; missing or denied EXE launch is an unavailable error, without auto-build or fallback.

The packaged host is intended for routine cooperating desktop use. Native framework calls, pipe writes or device cancellation can stall; this is not a hard real-time or hostile-process sandbox. A stop immediately suppresses Python transcript submission, while actual device cancellation remains asynchronous. CPU tests inject a simulated process and verify command bounds, callbacks, session cancellation, echo suppression and normal exit. They do not compile C#, enumerate installed engines, record a microphone or play audio. Those require a separately supervised real check.
